TTS / RADIO HANGING ON "thinking..."
  Two real bugs found while tracing it:
  a) lib/commands.js dispatched every command as `return doThing(inter)`
     inside a try/catch. A returned promise is not awaited there, so a
     rejection skipped the catch entirely and nothing ever replied.
     Now `return await` on every branch.
  b) lib/discord.js interactionEdit silently returned false when it had
     no application id. Deferring works without one, editing does not -
     which is exactly "thinking forever". It now logs loudly.
     CHECK DISCORD_CLIENT_ID IS SET IN RAILWAY. If it is missing that is
     very likely your whole problem.
  c) A watchdog in lib/staff.js force-answers after 50 seconds with the
     voice stage actually reached, so a command can never hang silently
     again. Run /tts after deploying and send me what it says.

TTS AND RADIO - THE ACTUAL CAUSE, FOUND
=============================================================
Close code 4017 means "end to end encryption required". Discord now
enforces E2EE on voice calls (the DAVE protocol).

@discordjs/voice asks the @snazzah/davey package which DAVE version it
supports. With davey MISSING that returns null, so the bot's identify
says max_dave_protocol_version: 0 - "I do not support encryption" -
and Discord hangs up at once. That is exactly your trace: it reached
"identifying" and closed with 4017.

FIXED IN THIS ZIP - package.json now has
    "@snazzah/davey": "^0.1.12"
    "@discordjs/voice": "^0.19.2"   (was 0.18.0)
Deploy and Railway installs it on build. Nothing else to do.
Verified here: with davey present DAVE_PROTOCOL_VERSION reads 1, so
identify advertises 1 instead of 0.

My earlier guess that it was blocked UDP was WRONG. The 4017 message
now says all of the above in the Discord reply.

YOUTUBE PLAYLISTS - plays through on its own
  Paste a playlist link on the site and it becomes the background
  rotation. YouTube's own player walks through it song by song and it
  loops at the end. No API key needed - the player does the advancing.

  HOW IT BEHAVES
    Queue empty      -> the playlist plays
    Someone requests -> the request jumps in front
    Queue empties    -> the playlist picks up again
    Playlist ends    -> it starts over

  The track title updates as it moves through, read from the player.

  WHICH LINKS WORK
    youtube.com/playlist?list=PL...        yes

    youtube.com/watch?v=X&list=PL...       adds the SINGLE SONG
    Watch Later / Liked                    refused, they are private

THREE PLAYLIST BUGS FIXED

1. "That did not work" on every playlist link
   The add route did out.track.title, but a playlist response has no
   .track - so it threw a TypeError, returned 500, and the site showed
   the generic failure. The playlist WAS being saved; you just always
   got told it failed. The route handles both shapes now, and the site
   says "Playlist set: <name>" instead of pretending it queued a song.

2. Remove sent you to Settings
   The button posted to a /settings/ route that always redirected to
   the settings page, even though the card you clicked it from is on
   the home page. It now returns you to the page you were on.

3. The player did nothing and never said why
   Two causes:
   a) If the poll finished before the YouTube player had finished
      loading, playList() silently gave up and nothing retried in that
      path. It now waits and retries until the player is ready.
   b) YouTube refuses to embed a lot of YouTube Music and
      auto-generated playlists - error 101/150 - and the old code
      swallowed that completely. The player now reads the error code
      and says what happened on screen:
        101/150 -> will not embed, use an ordinary playlist
        2/100   -> private or deleted

   YOUR LINK was music.youtube.com. If it still refuses after
   deploying, that is YouTube blocking that specific playlist, not the
   site. Make a normal playlist on youtube.com and use that link.

THE TTS VOICE
  The cause is espeak-ng itself. It is a formant synthesiser - it does
  not use recordings of a person at all, it generates the sound from
  scratch. That is why it is hard to follow. No amount of tuning makes
  it sound human.

  nixpacks.toml now installs mbrola plus two voices:
      mbrola, mbrola-us1, mbrola-en1
  mbrola stitches together recordings of a real speaker, so it is far
  easier to understand. It costs nothing, needs no API key, and runs
  on the same box. Deploy and it is there.

  A VOICE PICKER in Settings > Site > The voice:
    Natural, American      mb-us1   <- new default once mbrola is in
    Natural, British       mb-en1
    Robotic, American      en-us
    Robotic, British       en-gb    <- what you had
    Robotic, well spoken   en-gb-x-rp
    Robotic, deeper        en-us+Alex
    Robotic, female        en-us+f3
  Plus speed and pitch. No redeploy needed to change any of it - the
  natural ones are greyed out until mbrola is actually installed, and
  the card says so.

  Speed dropped from 165 to 150 words a minute. The old setting was
  fast enough to hurt on its own.

  The audio chain also got a highpass at 90Hz to cut rumble and
  dynaudnorm to even out the volume, so quiet words stop disappearing
  under game audio. Verified end to end: 3.2 seconds of clean 48k
  stereo out of the pipeline.
